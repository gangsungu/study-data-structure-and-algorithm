## 해시 테이블

키(key)를 **해시 함수에 넣어 배열의 인덱스를 계산해** 값(value)을 저장하는 자료구조다.
[배열](../02-배열과-리스트/배열과-리스트.md)은 "몇 번째"를 알아야 O(1)로 꺼낼 수 있지만, 해시 테이블은 **"무엇"만 알면** O(1)로 꺼낸다.
그 대신 순서가 사라지고, 계산한 인덱스가 겹치는 **충돌**을 직접 처리해야 한다.
자바에서는 `HashMap`(키-값), `HashSet`(중복 없는 값)으로 쓴다.

### 해시 테이블
+ 내부는 결국 **배열(버킷 배열)** 이다
    - 키를 해시 함수에 넣어 나온 숫자를 배열 인덱스로 사용한다
    - 탐색이 아니라 **계산**으로 위치를 찾기 때문에 데이터가 100만 개여도 한 번에 간다

    ```
    put("apple", 100)

    "apple" ──해시 함수──▶ 93029210 ──% 8──▶ 2   ← 이 계산이 O(1)
                                              │
    버킷 배열  [0][1][2][3][4][5][6][7]        │
                     ▲────────────────────────┘
               ("apple", 100) 저장
    ```

+ 평균 O(1)이지 **항상 O(1)이 아니다**
    - 모든 키가 같은 버킷으로 몰리면 한 줄로 늘어서서 O(n)이 된다
    - 그래서 "좋은 해시 함수"와 "적재율 관리"가 성능의 전부다

|연산|설명|평균|최악|
|---|---|---|---|
|`put(k, v)`|키-값 저장 (키가 있으면 덮어씀)|O(1)|O(n) → 자바 8+ O(log n)|
|`get(k)`|키로 값 조회|O(1)|O(n) → 자바 8+ O(log n)|
|`remove(k)`|키로 삭제|O(1)|O(n) → 자바 8+ O(log n)|
|`containsKey(k)`|키 존재 확인|O(1)|O(n) → 자바 8+ O(log n)|
|전체 순회|모든 키-값 방문|O(n + 버킷 수)|-|

> 값으로 찾는 `containsValue()`만은 예외다. 값은 해싱되지 않으므로 전부 훑어서 **O(n)** 이다.

```java
import java.util.HashMap;
import java.util.Map;

Map<String, Integer> table = new HashMap<>();

// 저장 (같은 키면 덮어쓴다)
table.put("apple", 100);
table.put("banana", 200);
table.put("cherry", 300);

// 조회 - 없는 키는 null이므로 기본값을 주는 편이 안전하다
table.get("banana");                    // 200
table.get("melon");                     // null
table.getOrDefault("melon", 0);         // 0

// 존재 확인 · 삭제
table.containsKey("apple");             // true
table.remove("cherry");

// 없을 때만 넣기 · 있으면 갱신 (개수 세기에 자주 쓴다)
table.putIfAbsent("apple", 999);        // 이미 있으므로 무시
table.merge("apple", 1, Integer::sum);  // 101

// 순회 - 순서는 보장되지 않는다
for (Map.Entry<String, Integer> e : table.entrySet()) {
    System.out.println(e.getKey() + " = " + e.getValue());
}
```

+ 해시 테이블이 못 하는 일
    - **정렬 · 범위 검색** : "10 이상 20 이하인 키" 같은 질문에는 전부 훑는 수밖에 없다 → `TreeMap`
    - **순서 보장** : 넣은 순서도, 정렬 순서도 지켜주지 않는다 → `LinkedHashMap`, `TreeMap`
    - **메모리** : 빈 버킷을 미리 들고 있어야 하므로 저장한 데이터보다 공간을 더 쓴다 ([시공간 트레이드 오프](../01-자료구조-개요/시간복잡도와-공간복잡도.md))

### 해시 함수
+ 임의의 입력을 **고정된 범위의 정수**로 바꿔주는 함수
+ 좋은 해시 함수의 조건
    - **빠른 계산** : O(1)이어야 한다. 해시 계산이 느리면 O(1) 검색의 의미가 없다
    - **결정성** : 같은 입력은 언제나 같은 해시 값을 낸다
    - **고른 분포** : 특정 버킷에 몰리지 않아야 한다
    - **충돌 최소화** : 다른 입력은 되도록 다른 값을 내야 한다

```java
// 문자의 아스키 값을 단순히 더하는 해시 - 나쁜 예
int badHash(String key, int size) {
    int sum = 0;
    for (char c : key.toCharArray()) {
        sum += c;
    }
    return sum % size;   // ← 버킷 범위로 접는 이 과정이 반드시 필요하다
}

// 자리마다 31을 곱해 순서 정보를 살린 해시 - String.hashCode()의 방식
int goodHash(String key, int size) {
    int hash = 0;
    for (char c : key.toCharArray()) {
        hash = 31 * hash + c;
    }
    return Math.floorMod(hash, size);   // hash가 음수일 수 있어 floorMod를 쓴다
}
```

+ 왜 `% size`가 필요한가
    - 해시 값은 수십억까지 나올 수 있지만 버킷 배열은 유한하다
    - **나머지 연산으로 배열 범위 안에 접어 넣어야** 인덱스로 쓸 수 있다
    - 이때 `size`를 **소수**로 두면 분포가 고르다
        + 자바는 대신 버킷 수를 2의 거듭제곱으로 잡고 `hash & (size - 1)`로 계산한다 (나눗셈보다 비트 연산이 빠르다)
        + 이러면 하위 비트만 인덱스에 반영되므로, 해시 값의 **상위 16비트를 하위로 XOR해 섞는 보정**을 먼저 넣는다
+ 왜 자릿수마다 곱하는가
    - 단순히 더하면 **글자 순서 정보가 사라진다**
    - `"abc"`, `"acb"`, `"cba"`의 합이 전부 같아서 애너그램이 통째로 한 버킷에 몰린다
    - 자리마다 31을 곱하면 순서가 다르면 값도 달라진다

+ 자바에서 직접 만든 클래스를 키로 쓰려면 `hashCode()`와 `equals()`를 **함께** 재정의해야 한다
    - 해시 테이블은 **`hashCode()`로 버킷을 찾고, 그 버킷 안에서 `equals()`로 진짜 키를 가린다**
    - 둘 중 하나만 재정의하면 넣은 값을 다시 못 찾는다

    |규칙|이유|
    |---|---|
    |`equals()`가 `true`면 `hashCode()`도 같아야 한다|버킷이 다르면 비교 자체를 못 한다|
    |`hashCode()`가 같다고 `equals()`가 `true`인 건 아니다|그게 바로 충돌이다|
    |키로 쓸 객체는 **불변**이어야 한다|넣은 뒤 필드를 바꾸면 해시 값이 달라져 영영 못 찾는다|

    ```java
    record Point(int x, int y) { }   // record는 equals/hashCode를 자동 생성한다

    // 직접 만든다면
    @Override public int hashCode() {
        return Objects.hash(x, y);
    }
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point p)) return false;
        return x == p.x && y == p.y;
    }
    ```

### 충돌 (Collision)
+ 서로 다른 키가 같은 버킷으로 계산되는 것
+ **충돌은 피할 수 없다**
    - 입력의 가짓수는 무한한데 버킷은 유한하다 (비둘기집 원리)
    - 그래서 해시 테이블의 설계는 "충돌을 없애는 법"이 아니라 **"충돌을 어떻게 감당할 것인가"** 다

#### 체이닝 (Separate Chaining)
+ 같은 버킷에 들어온 데이터를 **연결 리스트로 이어 붙이는** 방식
+ 조회는 버킷을 찾은 뒤 그 줄에서 `equals()`로 하나씩 비교한다

```
h("apple") = 2,  h("grape") = 2   ← 충돌

버킷 배열
[0] → null
[1] → null
[2] → ("apple",100) → ("grape",300)   ← 같은 버킷에 줄줄이 매달린다
[3] → ("banana",200)
```

+ 장점 : 구현이 단순하고, 적재율이 1을 넘어도 동작한다. 삭제가 깔끔하다 (노드만 떼면 끝)
+ 단점 : 노드마다 참조를 들고 있어 메모리를 더 쓰고, 줄이 길어지면 O(n)이 된다

#### 개방 주소법 (Open Addressing)
+ 충돌하면 **같은 배열 안의 다른 빈 칸**을 찾아 저장하는 방식. 연결 리스트를 쓰지 않는다
+ 빈 칸을 찾아가는 규칙에 따라 세 가지로 나뉜다

+ **선형 탐사 (Linear Probing)**
    - 충돌하면 옆자리를 순서대로 검사한다 : `(h + 1), (h + 2), (h + 3) …`
    - 메모리가 연속적이라 캐시 적중률이 좋고, 실제로는 매우 빠르다
    - **1차 클러스터링** : 값이 한 곳에 뭉치면 그 덩어리가 계속 커져서 탐사가 길어진다

    ```
    index: [0][1][2][3][4][5][6]
    data:  [ ][ ][ ][A][B][C][ ]   ← 3에서 시작한 충돌이 덩어리를 만든다
                     └──▶ h=3인 키가 또 오면 4,5를 지나 6까지 가야 한다
    ```

+ **이차 탐사 (Quadratic Probing)**
    - 간격을 제곱으로 늘려 멀리 건너뛴다 : `(h + 1²), (h + 2²), (h + 3²) …`
    - 덩어리를 건너뛰므로 1차 클러스터링이 줄어든다
    - 대신 **해시 값이 같은 키끼리는 여전히 같은 경로**를 밟는다 (2차 클러스터링)
    - 모든 칸을 다 훑지 못할 수 있다 → 버킷 수를 소수로 두고 적재율을 0.5 이하로 유지해야 빈 칸을 찾는 것이 보장된다

+ **이중 해싱 (Double Hashing)**
    - 두 번째 해시 함수의 결과를 **이동 간격(step)** 으로 쓴다 : `h1 + (i × h2)`
    - 키마다 탐사 경로가 달라져 클러스터링이 거의 없다. 분산 효과가 가장 좋다
    - 조건 : `h2`는 **절대 0이 되면 안 되고**(제자리걸음), 버킷 수와 **서로소**여야 모든 칸을 훑을 수 있다
    - 흔한 구성 : 버킷 수를 소수 `m`으로 두고 `h2 = 1 + (key % (m - 1))`
    - 대신 해시 함수를 두 번 계산하므로 선형 탐사보다 계산 비용이 크고 캐시에도 불리하다

+ 개방 주소법의 삭제 문제
    - 지운 자리를 그냥 비우면 **탐사 경로가 끊겨** 뒤에 있던 값을 못 찾는다
    - 그래서 "여긴 지워졌지만 지나가던 길이었다"는 **삭제 표시(tombstone)** 를 남긴다
    - 삭제가 잦으면 tombstone이 쌓여 탐사가 느려지므로 주기적으로 재정리해야 한다

    ```
    h(A) = 3, h(B) = 3 → B는 충돌해서 4번에 저장된다
    index: [0][1][2][3][4][5][6]
    data:  [ ][ ][ ][A][B][ ][ ]

    ❌ A를 그냥 비우면
    data:  [ ][ ][ ][ ][B][ ][ ]
           get(B) → 3번부터 탐사 → 3번이 비었으니 "없음" 판정

    ✅ 삭제 표시를 남기면
    data:  [ ][ ][ ][X][B][ ][ ]      X = 삭제됨(tombstone)
           get(B) → 3번은 X니까 계속 → 4번에서 B 발견
    ```

#### 체이닝 vs 개방 주소법

|기준|체이닝|개방 주소법|
|---|---|---|
|저장 위치|버킷 밖 (연결 리스트)|배열 안|
|적재율|1을 넘어도 동작|1을 넘을 수 없음 (보통 0.5~0.7 유지)|
|삭제|노드만 제거하면 끝|tombstone 필요|
|메모리|노드 참조 오버헤드|추가 구조 없음|
|캐시 지역성|나쁨 (노드가 흩어짐)|좋음 (연속된 배열)|
|약점|줄이 길어지면 O(n)|클러스터링, 삭제 처리|

+ 실제 구현
    - **자바 `HashMap`은 체이닝**이다. 자바 8부터는 한 버킷의 노드가 8개를 넘고 전체 버킷이 64개 이상이면 그 버킷을 **레드-블랙 트리로 전환**해 최악을 O(n) → O(log n)으로 낮춘다 (6개 이하로 줄면 다시 리스트로 되돌린다)
    - **파이썬 `dict`는 개방 주소법**이다. 체이닝이 아니라 무작위성을 섞은 탐사(perturbation)를 쓰며, 3.7부터는 삽입 순서 배열을 따로 둬서 순서를 보장한다

### 적재율과 리사이징
+ **적재율(Load Factor)** = 저장된 데이터 수 ÷ 버킷 수
    - 이 값이 높아질수록 충돌이 급격히 늘어난다. 해시 테이블 성능은 사실상 이 숫자 하나로 결정된다
+ **리사이징(재해싱)**
    - 적재율이 임계값을 넘으면 버킷 배열을 보통 **2배로 늘리고 모든 키를 다시 배치**한다
    - 버킷 수가 바뀌면 `% size` 결과가 달라지므로 **기존 위치를 그대로 옮길 수 없다**. 그래서 "재해싱"이다
    - 이 작업은 O(n)이지만 가끔만 일어나므로, 나눠 보면 삽입은 여전히 평균 O(1)이다 ([분할 상환 분석](../01-자료구조-개요/시간복잡도와-공간복잡도.md))
+ 자바 `HashMap` 기본값 : 초기 용량 16, 적재율 0.75 → **13번째 삽입에서 32로 늘어난다**
+ 담을 개수를 안다면 **초기 용량을 지정해 리사이징을 피한다**

```java
// 1000개를 넣을 예정이라면 1000 / 0.75 ≈ 1334 → 그 이상인 2의 거듭제곱 2048
Map<String, Integer> table = new HashMap<>(2048);
```

### 자바 구현체 고르기

|구현체|순서|특징|비고|
|---|---|---|---|
|`HashMap`|없음|가장 빠르다. 기본 선택|`null` 키를 1개 허용|
|`LinkedHashMap`|삽입 순서|연결 리스트를 덧붙여 순서 유지|LRU 캐시 구현에 쓴다|
|`TreeMap`|키 정렬 순서|해시가 아니라 **레드-블랙 트리**. 모든 연산 O(log n)|범위 검색 가능|
|`HashSet`|없음|내부가 `HashMap`이다 (값 자리에 더미 객체)|중복 제거용|
|`ConcurrentHashMap`|없음|여러 스레드에서 안전|`Hashtable`은 레거시라 쓰지 않는다|

+ 정렬이나 범위 검색이 필요 없다면 **`HashMap`이 정답**이다
+ `Hashtable`은 `java.util.Stack`처럼 모든 메서드에 동기화가 걸린 레거시 클래스다. 멀티스레드라면 `ConcurrentHashMap`을 쓴다

### 정리
+ 해시 테이블은 **"탐색을 계산으로 바꾼"** 자료구조다
+ 평균 O(1)은 공짜가 아니라 **고른 해시 함수 + 낮은 적재율**이 유지될 때만 성립한다
+ 충돌 처리(체이닝 · 개방 주소법)와 리사이징이 그 조건을 지켜주는 장치다
+ 그 대가로 **순서와 범위 검색을 포기하고, 메모리를 더 쓴다**
